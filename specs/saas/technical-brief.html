Agentrix WebAgent Platform

Technical brief: a payments ecosystem of autonomous agents on adk-rust and PayPal

Zavora Technologies Ltd · PayPal AI Hackathon · 12 November 2026 · Code: github.com/zavora-ai/agentrix-saas (MIT) · Live: paypal.agentrix.website · Everything described here runs on the PayPal sandbox.

1. Summary

Agentrix turns a business's website into a team of AI agents ("WebAgents") that sell, bill, collect, pay and settle with other businesses' agents. The design goal is that an agent may move money without a human in the loop only when three things can be verified by a party that does not trust the agent: who the agent is, who is accountable for it, and where the money went.

  • Identity. Every agent has a did:web identifier under its site's own domain, a badge signed by the owner's key, and signs each cross-company request with HTTP Message Signatures (RFC 9421).
  • Authority. The owner signs a mandate that bounds what an agent may pay. Payment tools run on a governed path where deterministic rules, not model output, decide whether a call may reach PayPal.
  • Evidence. Every money movement is confirmed by reading it back from PayPal, recorded in a signed append-only wallet log, and posted to the books under the PayPal identifier.

The system ran unattended on the sandbox for about 23 hours before submission. In that time three customer agents placed 18 orders and paid for 14 of them with vaulted PayPal payment tokens (USD 109.88 captured), two companies' agents settled eight invoices with each other, and payroll was paid through Payouts. All figures in this brief were read from the live system or from PayPal's API.

3. Agent autonomy design

Autonomy comes from adk-rust's Agent Kernel (adk-kernel), a resident supervisor with a process model, wake semantics, an event bus and a control plane. Three properties shape how the agents behave.

  • Always resumable, not always running. Each agent activity is a durable process. A sleeping process is in the Waiting state with a recorded wake set and makes no model call. State is kept in the kernel's stores, so a restart loses nothing and a missed schedule fires once on recovery.
  • Every wake is a governed run. An agent never calls a tool outside a run, so policy, guardrails, approvals, spend limits and the audit log apply to scheduled and event-driven work exactly as they do to interactive work.
  • Work starts from a wake, not from a prompt. The kernel wakes an agent on a schedule (cron), at a moment (for example an instalment's due date) or on an event (an invoice arriving at the agent door, a verified PayPal webhook, a message from the owner).

Autonomy is bounded in four ways. The mandate limits what an agent may pay on its own. A call outside the mandate becomes a held decision for the owner rather than an error. The owner can revoke one agent, which stops its next token exchange, or freeze the whole company, which denies every money tool. Each business has a daily model spend cap enforced by the gateway, so a looping agent stops at a known cost.

4. Multi-agent architecture

Each business is a small organisation of specialised agents rather than one general agent. Every agent has one job, its own identity and keys, and only the tools that job needs. The agents of a business coordinate through the kernel's event bus and through shared records (the books, the wallet, the order records), not through free-form conversation with each other, which keeps their behaviour auditable.

Between businesses there is no shared memory and no shared process. Agents of different businesses interact only through each site's agent door, with signed requests and mandates on both sides (section 7.1). The same pattern scales from two companies on one node to one isolated node per business.

5. Agent identity

5.1 Identifiers and badges

Each site is a DID subject: did:web:<site-host> resolves to /.well-known/did.json. Each agent is did:web:<site-host>:agents:<role>, with its DID document at /agents/<role>/did.json and its badge at /agents/<role>/badge.json. A badge is a JSON document carrying the agent's role, site, sponsor (the accountable human), key thumbprints, mandate reference, wallet checkpoint and a JsonWebSignature2020 proof (EdDSA) made with the site's #owner key. The hosting platform adds a voucher that it hosts the site.

Verification is public at GET /agents/verify?did=… and runs ten checks: the DID document resolves from the site's own domain; the badge is signed by the owner key; the badge names this agent and site; the key is in the agent's DID document and in the site's key directory; the names match; the agent is active; the agent holds no secrets; the platform vouches for the site; and the agent card is signed by the owner key.

5.2 Request signing

Every request from one company's agent to another carries an HTTP Message Signature (RFC 9421, Web Bot Auth profile). The verifier requires:

  • Content-Digest: sha-256=:…: (RFC 9530) over the body;
  • Signature-Agent naming the signer's site, from which the verifier fetches /.well-known/http-message-signatures-directory;
  • Signature-Input covering @authority, @method, @path and content-digest, with alg="ed25519", created, expires and tag="web-bot-auth"; the key id is the JWK thumbprint.

A request that fails is answered with HTTP 401 and a sealed refusal receipt: a body with the refusal code (content_digest_required, signature_required, signature_invalid, mandate_used, plan_refused), the claimed agent, the request digest and nothing_moved: true, signed by the refusing company's key. The refusal is also written to that company's audit log. No PayPal call is made for a refused request.

5.3 Tokens and cloud federation

Each site is an OpenID Connect issuer for its agents (/.well-known/openid-configuration and a JWKS). Inside the node, an agent holds no long-lived secret: when a tool needs PayPal, the token service exchanges the agent's identity for a short-lived token scoped to one resource and role (RFC 8693 style), and revoking an agent stops its next exchange without rotating any PayPal credential.

We verified that the same issuer is accepted by AWS IAM (AssumeRoleWithWebIdentity), Amazon Bedrock AgentCore Identity (GetWorkloadAccessTokenForJWT), Google Cloud workload identity federation (STS token exchange) and Microsoft Entra Agent ID (federated identity credential on an agent identity blueprint). In the other direction, the door's verifier accepts tokens from trusted external issuers. This code is upstream in adk-rust's adk-auth crate (zavora-ai/adk-rust#1362).

6. Authority: mandates and the governed path

A model can propose a payment; it cannot authorise one. Each payment tool call passes through a governed path that evaluates deterministic policy before any effect runs.

ControlRule enforced before a PayPal call
Intent mandateSigned by the owner. Sets the maximum per payment, the maximum per day, the allowed payees and an expiry. Mandates follow the structure of the Agent Payments Protocol (AP2); we describe them as AP2-style and do not claim conformance.
Cart mandateIssued per invoice for agent-to-agent settlement. It is single-use: presenting it again is refused with mandate_used.
Payee bindingA bill can only be paid to the payee the books hold for that vendor. A message claiming changed bank or PayPal details cannot change the payee; the change goes to the owner.
Refund bindingA refund goes only to the payer of the original capture, read from PayPal's capture record, never from the conversation.
Approval bindingWhen a call exceeds the mandate it is held for the owner. The owner's WebAuthn assertion signs a fingerprint of the exact tool call and arguments. If the agent changes any argument, the fingerprint changes, the earlier approval is void, and the new call is held again.
Input screeningInbound email and documents are parsed in a sandbox with the network denied and screened for payee-change claims, urgency and injected instructions before an agent sees them.

A committed suite of ten attacks exercises these rules, including a business-email-compromise invoice, an injected refund to an attacker's address, an edit after approval, a forged PayPal webhook, a replayed cart mandate and a request signed with an unknown key. All ten were refused. Each result is scored from PayPal's API, the books and the signed audit log, not from model output.

7.2 Correctness under failure

  • Lost responses. If the node crashes or loses the response after sending a capture or payout, the outcome is marked unknown and resolved by reading PayPal back. The webhook path completes the same record, and the tests assert that both paths together post exactly once.
  • Duplicate and out-of-order events. Events are de-duplicated by event id, and state only moves forward, so a resent older event changes nothing.
  • Forged events. A body that fails PayPal's signature verification is answered with 401 and posts nothing.
  • Reconciliation. Every hour the Payables agent re-reads each wallet entry from PayPal and signs a checkpoint that records whether the wallet and PayPal agree.

8. Evidence: wallet, books and audit

The money stays in PayPal. The wallet is a per-business, append-only log of entries (capture, fee, payout, refund), each with the PayPal id, the counterparty and the order or invoice it belongs to. Entries are hashed into a Merkle tree; each checkpoint signs the root and the result of reconciliation. A wallet entry is "three-way matched" when the wallet entry, PayPal's record and the journal in the books agree. An agent's badge points to the latest checkpoint, so anyone verifying the agent can see whether its wallet matches PayPal.

Each business also keeps a signed audit log (adk-rust's audit log with signed checkpoints) of every model call, tool call, approval, denial and refusal. The log can be verified offline with agentrix-saas audit verify <log> --key-file <key>; changing one byte makes verification fail.

9. The customer path

A customer can order through the pages or in the conversation. When a visitor tells the front desk what they want (for example "I'd like two loaves"), the Orders desk resolves the product and quantity against the catalogue, checks the day's stock, prices the order from the live price list, and returns an order card in the chat with the lines, the total in local currency and US dollars, and a PayPal button. The button places the lines in the bag and proceeds to checkout, where the order is paid through PayPal. Paid orders are confirmed by the Cashier agent and can be tracked by order number.

A customer's agent follows the same rules through the agent door. Requests that create obligations must be signed; the order records the proven agent identity, the proof method and who vouched for it. Custom orders are held for the owner and nothing is charged until the owner approves.

Known limitations

  • Sandbox only. The businesses, customers and staff are sample data.
  • The order card in the chat proceeds to checkout; payment is not yet completed inside the conversation, and checkout requires the customer to sign in.
  • No shop on the live build holds an approved PayPal subscription; the subscription plans exist and the lifecycle calls are implemented.
  • Supplier, courier and rider businesses are designed but not built.
  • Owner passkeys are not yet enrolled on the two money consoles of the judged build, so mandates there were signed with the owner key file.
  • The "Run the day" button on the judges' page runs on an isolated node with scripted model answers and in-memory books; its PayPal calls are real sandbox calls.
  • The platform company's cash figure on its console drifts from PayPal and is under investigation.

12. Stack

Rust (axum, tokio, sqlx/SQLite); adk-rust crates adk-kernel, adk-agent, adk-runner, adk-graph, adk-guardrail, adk-memory, adk-auth, adk-awp, adk-sandbox and adk-server; Anthropic Claude (Sonnet for the Chief and Receivables, Haiku for Payables) and Vultr Serverless Inference (Qwen for the front desks, Nemotron for content screening); Zavora ERA on PostgreSQL through mcp-erp; Caddy; AG Grid / AG Studio for the treasury board; one Vultr VM for the judged build, with a Vultr Kubernetes cluster prepared for one isolated node per business.
