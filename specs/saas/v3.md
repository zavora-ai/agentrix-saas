## Technology 1: the badge

**Problem.** Agents here are `urn:adk:agent:<company>/<role>`. That name is stable and every audit record carries it, but nobody outside can look it up.

**Design.** The website's own domain is the root of trust. Nothing depends on a registry.

| Part | What it is | State |
|---|---|---|
| Identifier | `did:web:<site-host>:agents:<role>`, served at `https://<site-host>/agents/<role>/did.json`. The site itself is `did:web:<site-host>` | New |
| Keys | The Ed25519 keys each company already publishes in its Web Bot Auth key directory (`kid` `agent:<role>`, `owner`) | Built (`saas-settle/src/keys.rs`) |
| Link to the internal name | The DID document lists the `urn:adk:agent:…` id under `alsoKnownAs`. Policy files and audit records keep the URN | New, small |
| Proof on each request | RFC 9421 signed requests, checked at the door before any PayPal order exists | Built (`saas-settle/src/door.rs`) |
| Badge | `GET /agents/<role>/badge.json`, signed by the site's `owner` key: the DID, role, site, sponsor (the owner, and the passkey that vouches), the PayPal link, the mandate's digest, the wallet's latest checkpoint, active or frozen | New |
| Who vouches for the site | Agentrix (`did:web:paypal.agentrix.website`) signs that it hosts the site and checked its PayPal link | New |
| Signed agent card | The A2A card at `/.well-known/agent-card.json` carries a JWS signature | Card exists unsigned. adk-awp already signs cards for the AWP edge; reuse that signer |
| Verify | A page and a command (`agentrix-saas badge verify <did>`) that resolve the DID and check every signature | New |

### Compatibility with the cloud providers' agent identities (must-have)

All three clouds speak the same two wire formats: OIDC tokens checked against a published key set, and SPIFFE-style ids. So each site becomes a small OIDC issuer for its own agents, and each door learns to check the clouds' tokens.

| Direction | What happens | State |
|---|---|---|
| **Out: our agent proves itself to a cloud** | The site serves `/.well-known/openid-configuration` and a key set. It issues a short-lived token per agent: `iss` the site, `sub` the agent's DID. The cloud accepts it through its own federation, with no cloud secret stored anywhere | New |
| **In: a cloud's agent proves itself to us** | The door accepts a token from a trusted issuer, checks it against that issuer's published keys, and maps its claims onto `AgentPrincipal`. The badge page shows who vouched | New on the door. adk-auth's `sso` feature already validates tokens against published keys, with Azure and Google providers |

| Cloud | Their model | Out (they accept ours) | In (we accept theirs) |
|---|---|---|---|
| Microsoft Entra Agent ID | Agent identities sign in only through federated credentials on their blueprint | A federated credential naming our issuer and the agent's DID | Tenant issuer; `azp` is the agent, the blueprint is the class, `xms_act_fct` / `xms_sub_fct` mark an agent token |
| Amazon Bedrock AgentCore Identity | Workload identity per agent; an inbound authorizer that takes an OIDC discovery URL | Our discovery URL in the inbound authorizer; an IAM OIDC provider for plain AWS roles | Whatever issuer the AgentCore agent is configured with |
| Google Agent Identity | A SPIFFE id and a 24-hour certificate per agent | Workload Identity Federation with our issuer | The SPIFFE id as the `AgentId` (it already accepts `spiffe://`); how an outside party checks it is not yet read |

### At the sample sites' agent door: an agent is known only when it proves it

**Decided by James, Wed 11 Nov 2026, about 06:55 EAT** ("Verify at sample doors"), after the walk on the
server (`walk-2026-11-11.md`) found that the door called any agent "known" once it named itself.

- **Anonymous** stays as it is: search the catalogue, check slots, an order's status, ask a question.
- **Known** means the request proves who the agent is, in one of two ways:
  1. an RFC 9421 signature whose `Signature-Agent` names a key directory, checked against that directory (the check the settlement door already makes); or
  2. a bearer token from an issuer the site trusts, addressed to this site's door: another Agentrix site's issuer, or a cloud agent token read through `saas-federation` (Entra Agent ID, Google agent identity).
- **A name alone proves nothing.** `clientInfo.name` or a bare `Signature-Agent` header is recorded as "claimed" and gives no rights.
- **Known-only tools** (`quote.create`, `checkout.create`, `request_custom_order`) refuse an unproven caller before anything is created: no quote, no checkout link, no held request. The refusal is a signed receipt in the settlement door's shape (`nothing_moved: true`, the claimed agent, a code such as `agent_identity_required`).
- **What a proven agent leaves behind:** the quote, the checkout link or the held request names the agent's verified id and who vouched for it, and the owner's decision card shows both.
- **Words on the site:** `/agents` and the AWP manifest drop "Signatures aren't verified on the samples yet" and say what proof the door takes.
- **The door still never pays.** A proven agent can prepare a checkout link for a person; the video says that, not "the agent orders".

**Acceptance, checked from outside after the deploy:**

| Call to a known-only tool | Expected |
|---|---|
| No signature, no token | Refused, signed receipt, nothing created |
| Only a claimed name | Refused, signed receipt naming the claim |
| A signature that does not verify, or a token with a tampered signature or another audience | Refused |
| Signed by an agent whose key is in a published directory | Accepted; the result names the verified agent |
| `tools/list` for an anonymous caller | Marks the known-only tools as needing proof, or leaves them out |

### No agent holds a secret, and the owner can revoke one agent

Postman, a partner of this hackathon with a judge on the panel, sells a product called **Passport** (generally available since September 2026): people and agents call APIs without holding the real credentials, permissions are set by identity, API and duration, and access is revoked without rotating keys. Two consequences:

- **The word.** Our identity document is called the **badge**, never "passport".
- **The same property, shown.** v2 already has it: each agent trades its own credential for a short-lived token bound to one resource and its role's scopes (`saas-company/src/sts.rs`), and the PayPal secret is never a tool argument, a tool result or a model message. v3 puts it on the badge ("holds no secrets; PayPal access is issued per call") and adds **Revoke** beside Freeze: the owner switches one agent off, its tokens stop working at the next check, and no PayPal key is rotated. Switching it back on takes the passkey.
- **Not planned:** integrating Passport itself. It runs as a proxy inside a customer's network and there is no time to evaluate it. Their webinar is on 13 Nov, after the deadline.
- **Cheap and worth doing:** a public Postman collection for the judges' path (resolve a DID, fetch a badge, verify it, send a signed and an unsigned order). Tick Postman on the form only if the collection ships.

## Technology 2: the passkey that links an agent to PayPal

The passkey ceremony already signs the exact call: the challenge is SHA-256(fingerprint ‖ nonce) (`saas-web/src/passkeys.rs`).

**The owner is prompted at three moments, and at no other:**

| Moment | What is signed | State |
|---|---|---|
| **Link PayPal** (once) | A binding record: the site, the owner's passkey, the PayPal ids PayPal itself returned, and the agents allowed to use them | New. Vault setup exists (`saas-settle`) |
| **Sign or raise the mandate** | The mandate's fingerprint | Built |
| **Step up** | One payment outside the mandate, to a new payee, or after a payee's details changed; unfreeze | Built for decision cards; the new-payee rule exists for vendors |

- Inside the mandate the agent pays without a prompt. It signs a cart mandate, and the receipt names it.
- The PayPal ids in the binding come only from PayPal's own response, never from a typed-in value.
- The binding is sealed with the `owner` key, written to the signed audit log, and shown in every badge of that site.

## Technology 3: the wallet

**What it is.** Each site has one wallet: an append-only, tamper-evident record of every movement on the business's PayPal account, each entry naming the agent that caused it, plus the spending limits each agent's mandate gives it. An agent's wallet is its view of that record. This follows adk-payments, where a wallet belongs to a site and the agent is an attribution on each payment. The money stays in PayPal, which has no per-agent accounts, so say "wallet record", never "holds funds".

- **Entry:** sequence, time, kind (capture, refund, payout, subscription, fee), amount, the PayPal object id, the counterparty, the order or invoice that caused it, the acting agent, the mandate or approval behind it.
- **Source:** only a verified PayPal webhook or a read-back from PayPal. Never the model, never the request.
- **Storage:** records in adk-auth's signed audit log (Merkle log with signed checkpoints), one log per site, each record carrying the PayPal id and the agent.
- **Sync:** each checkpoint records a reconciliation against PayPal. The wallet shows "matches PayPal as of 14:02" or "drift".
  - Baseline: read every PayPal object back, as the coordinator does today.
  - Stretch: the balances report (`/v1/reporting/balances`). Not checked in sandbox.
- **Books:** every entry posts to ERA through the PayPal clearing account. The wallet page shows the three-way match: wallet entry, PayPal id, ERA journal.
- **Board:** the wallet ledger and the three-way match are the AG Grid tables.

### What every PR must meet

- An issue first, referenced with `Fixes #N`. Branch `feat/`, `fix/`, `docs/`, `refactor/`, `test/` or `chore/`. Conventional commit subject. PR body with What, Why, How.
- A fragment in `changelog.d/` (`added.`, `fixed.`, `security.`, `changed.` or `breaking.` plus a slug). `CHANGELOG.md` is never edited by hand.
- A new feature flag is declared with `dep:` optional dependencies, gated in `lib.rs`, listed in the crate's feature doc and added to `scripts/feature-coverage-pairs.txt`.
- adk-core, adk-auth, adk-server and adk-payments are Stable: additions only, new fields optional or builder-defaulted, new enums `#[non_exhaustive]`.
- Errors are `thiserror` enums that convert into `AdkError` with a dotted code. Crypto is `aws-lc-rs`. Keys never appear in `Debug` output or logs.
- Rustdoc on every public item with an example and its errors; the matching `docs/official_docs` page and the crate README updated.
- Tests: unit and integration, `wiremock` for HTTP, property tests where there is an invariant, the conformance suites for stores and providers.
- Gates: `cargo fmt --check`, `clippy --workspace --all-targets -D warnings`, `cargo nextest run --workspace`, doctests, `scripts/validate-pr.sh`. Toolchain 1.95.0.
